# 12 - Interop and targets

## Targets

| Target | Status in version 1 | Runtime profile |
|---|---|---|
| Linux, macOS, Windows on x86-64 and AArch64 | tier 1 | `full` |
| RISC-V 64 Linux | tier 2 | `full` |
| `wasm32-wasi` (WASI preview 2, component model) | tier 1 | `single` |
| `wasm32-browser` (JS host bindings) | tier 2 | `single` |
| Bare-metal ARM Cortex-M, RISC-V 32, x86-64 (kernels) | tier 2 | `freestanding` |
| iOS, Android | tier 2, via the C ABI and platform toolchains | `full` |

Cross-compilation to any target from any host is built in (Zig, Go). The
compiler bundles the needed C runtime headers and libraries for each
target, as Zig does, so that `sisu build --target aarch64-linux` works on a
fresh machine.

## Runtime profiles

The runtime is what makes colourless tasks and capabilities work, and it
is the thing embedded and kernel developers cannot afford. Profiles make it
a dial, selected in the manifest:

- **`full`**: M:N task scheduler over OS threads, global allocator,
  panic unwinding, capability implementations backed by the OS. The
  default.
- **`single`**: one OS thread, an event loop; tasks are coroutines on it.
  For WebAssembly and for programs that want deterministic scheduling.
  Capabilities are backed by WASI or the JS host.
- **`freestanding`**: no scheduler, no global allocator, no unwinding
  (`panic = abort` or a user hook), no `std.cap` implementations. `std.core`
  and `std.collections` with an explicit allocator work; `task.scope` does
  not compile. The program supplies its own `System` by implementing the
  capability traits over its hardware, which is how a kernel exposes a
  file system to Sisu code running on it.

The capability traits are the seam: `Fs`, `Net`, `Clock` etc. are traits in
`std.cap` with the OS implementations in `full`/`single` and user
implementations in `freestanding`. This is Roc's platform split and Zig's
`Io` interface in one mechanism.

## C interop

C is the lingua franca ([`c.md`](../research/languages/c.md)) and the
research on Swift, Kotlin, Zig and Rust agrees that painless C interop is
an adoption prerequisite.

```sisu
import c "sqlite3.h" as sqlite           # header import: declarations generated by the compiler
import c "zlib.h" as zlib with link="z"

extern "C":                               # or declare by hand
    def strlen(s: ptr[c_char]) -> c_size

@export("sisu_compute")                   # callable from C
def compute(data: ptr[u8], len: c_size) -> i32: ...
```

- **Header import** (Zig's `@cImport`/`translate-c`): the compiler parses
  C headers with its bundled C front end and exposes the declarations as an
  `unsafe` module. No binding generator to run, no bindings to commit.
  Macros that are constants or simple expressions are translated; function-
  like macros are not (as in Zig, with the same documented limitation).
- **C types** are in `std.ffi`: `c_int`, `c_size`, `c_char`, `ptr[T]`,
  `ptr mut T`, `CStr`. `@repr(c)` on a struct or enum fixes its layout.
- **Calling C is `unsafe`** and is allowed only in `[trust]`-listed
  packages. The idiom is a thin trusted wrapper package that exposes a safe
  API taking capabilities, so that the rest of the program stays in safe
  Sisu.
- **Exporting** Sisu functions with the C ABI is first-class so that Sisu
  can be embedded in C, C++, Python, Swift, Kotlin or anything with a C FFI.
  `@export` requires `@repr(c)` types at the boundary; the compiler reports
  what is not representable.
- **Blocking C calls** are annotated `@blocking` so the scheduler moves
  them off the task threads ([06](06-concurrency-and-capabilities.md)).
- Linking C sources directly (`[build] c-sources = ["vendor/*.c"]`)
  compiles them with the bundled C compiler, as Zig's build system does.
  This removes the "install the right toolchain" step that blocks most
  first-time C-dependency builds.

## C++ interop

Not a goal. Carbon exists because C++ interop at the level of templates,
classes and exceptions requires designing the language around C++
([`carbon.md`](../research/languages/carbon.md)), and Swift's C++ interop
took five years for a partial result. Sisu interoperates with C++ through
`extern "C"` wrappers, as Rust, Go and Zig do. Open question Q-24.

## Other languages

- **Python**: Sisu exports C-ABI functions; `std.x.py` provides the CPython
  extension glue (PyO3's design) so that Sisu can be the fast layer under
  Python, which is the role Rust increasingly plays and Mojo targets.
- **JavaScript/Web**: WebAssembly with generated bindings for exported
  functions and capability implementations over Web APIs.
- **JVM/.NET**: via C ABI (JNI/P-Invoke). Not first-class.

## ABI

Sisu's own ABI is **not stable** between compiler versions. Rust's choice,
for Rust's reasons: an unstable ABI leaves layout, calling conventions and
monomorphisation free to improve. Swift's stable ABI ("library evolution")
cost years and a resilience model that affects every generic call, and
exists because Apple ships system frameworks in Swift; Sisu has no such
constraint. A stable ABI for dynamic libraries is open question Q-31; the
C ABI is the stable interface in the meantime, and `@repr(c)` plus
`@export` make it easy to use.

## Binary size and startup

- Static linking by default (Go, Rust, Zig): one file to deploy.
- Dead-code elimination at the item level, which the no-runtime-reflection
  rule ([08](08-metaprogramming.md)) keeps effective.
- `release-size` profile for embedded and WebAssembly.
- No startup work beyond constructing `System`: no class loading, no JIT
  warm-up, no global constructors (there are no global constructors; `const`
  is compile-time and lazily initialised statics are explicit `Lazy[T]`).
